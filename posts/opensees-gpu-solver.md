# 在 OpenSees 里塞进一块 GPU：把有限元求解加速 212 倍

本文基于本人毕业设计《OPENSEES 应用与高性能计算》整理。代码已开源：[OpenSees-GPU-Solver](https://github.com/Tilyes/OpenSees-GPU-Solver)，实施日志、基准日志、sm_120 复现器等全部过程文档都在仓库的 `plan/` 目录里。

**先说明归属**：OpenSees 是美国太平洋地震工程研究中心（PEER）主导开发的开源有限元框架，版权属加州大学董事会（The Regents of the University of California），仅限教育/研究/非营利机构的非商业用途。**本文的工作不是从零写一个有限元软件**，而是在 OpenSees 之上新增一个 GPU 线性求解器。除求解器、基准与文档之外，单元、材料、分析算法、Tcl 解释器全部是上游 OpenSees 的成果。

## 一、一切的终点，是一个线性方程组

结构工程里做有限元分析，不管是算一根悬臂梁还是一栋超高层，流程都是：几何建模 → 网格划分 → 单元刚度装配。做完这些之后，**所有物理问题最后都归结为解一个方程**：

```
K · u = F
```

- `K` —— 刚度矩阵，稀疏
- `u` —— 节点位移，我们要求的东西
- `F` —— 荷载向量

`K` 的规模随网格加密迅速膨胀。S1 这个算例（18×18×200 的三维实体块）有 **217,683 个自由度**。如果按稠密矩阵存，需要 217683² ≈ 4.7×10¹⁰ 个数，约 **376 GB** —— 一块 12GB 的显卡连零头都装不下。

但好消息是：刚度矩阵每一行只有少数几个非零元（一个节点只和相邻节点耦合），非零元总数 `nnz` 只有几百万。**稀疏性，是这类问题的全部希望。**

### 两条路线的分野

| | 直接法 | 迭代法 |
|---|---|---|
| 代表 | SuperLU（串行）、Mumps（并行） | CG、BiCGStab（本文） |
| 思路 | 对 K 做 LU 分解，一次性解出精确解 | 从一个猜测出发，一步步逼近 |
| 计算量 | 分解很贵，3D 问题会产生大量「填空」(fill-in) | 每步一次矩阵向量乘，O(nnz) |
| 内存 | 大（要存 L、U 因子，3D 下 fill-in 可达 O(n⁴ᐟ³) 个非零元） | 小（只存原矩阵） |
| 何时快 | 中小规模 | 大规模稀疏，尤其 3D |

所谓**填空**，是指 LU 分解会在原矩阵本来是 0 的位置上产生新的非零元。二维问题还算温和，三维问题里填空会爆炸式增长 —— 这是直接法在大规模 3D 问题上的结构性痛点，也是我选迭代法的第一个理由。

第二个理由更直接：**迭代法的每一步天然是并行的**。它的核心算子是稀疏矩阵向量乘（SpMV），只遍历非零元，不存在跨行的依赖，天生适合 GPU。

## 二、OpenSees 本身能并行到什么程度

OpenSees 并不是没有并行能力，它内置了两个并行版本，思路完全不同：

**OpenSeesSP** —— 面向单个大模型。主进程读取完整脚本、构建整个模型，执行到 `analyze` 时才做区域分解（用 METIS 图划分库按单元-节点图自动切分），各工作进程负责自己子域的单元状态确定，同时**协同组装并求解同一个全局方程组**。优点是使用近乎透明，把 `system` 换成并行求解器（最常用 Mumps）就行；缺点是要求所有单元和材料都正确实现了 `sendSelf/recvSelf`，兼容性有风险。

**OpenSeesMP** —— 面向参数研究、蒙特卡洛、IDA 这类任务。启动 N 个 MPI 进程，每个进程跑一个完整的 OpenSees 解释器，靠 `getPID` / `getNP` 在脚本里做任务分发。灵活性极高（不依赖序列化方法，支持全部单元材料），但需要用户自己理解 MPI 进程模型。

已有的公开案例也很能说明上限：141.8m 的框架-核心筒模型从 168 小时压到 11 小时；632m 的上海中心从 409 小时压到 27.5 小时。这些加速**来自线性方程组的并行求解，而不是非线性材料层面的自动并行** —— 也就是说，瓶颈依然在 `K·u = F` 上。

所以问题就变成了：**能不能把这一步直接搬到 GPU 上？** 这就是我的题目。

## 三、从 CSR 开始

在 GPU 上做稀疏计算，第一件事是选一个合适的数据结构。我用的是 CSR（Compressed Sparse Row，按行压缩）三数组：

```
rowPtr (长度 n+1)：第 i 行的第一个非零元在 colInd/val 里的下标
colInd (长度 nnz)：每个非零元的列号
val    (长度 nnz)：每个非零元的值
```

一个 4×4 的例子：

```
矩阵：                 CSR 表示：
[ 5  0  2  0 ]        rowPtr = [0, 2, 4, 5, 6]
[ 0  7  0  1 ]        colInd = [0, 2, 1, 3, 1, 3]
[ 0  8  9  0 ]        val    = [5, 2, 7, 1, 8, 9]
[ 0  0  0  3 ]
```

第 1 行（下标 0）从 `rowPtr[0]=0` 到 `rowPtr[1]=2`，即 `val[0..1] = [5,2]`，列号 `[0,2]`。以此类推。

这里有一个 OpenSees 内部的约定必须记住：**每一行的第一个非零元就是对角元，其后按列号升序排列**。我的三角求解 kernel 直接吃这条约定。

### CuSPSolver 的数据流

把这个求解器接进 OpenSees，一次 `solve()` 的流程是：

```
① 从 SOE 对象取 CPU 端指针（K、F、u 都是 OpenSees 在 CPU 上组装好的）
② 首次调用：上传 CSR 结构 + 创建 cuSPARSE 描述符 + 计算 SpMV 工作缓冲大小
③ 每次调用：上传 K 的数值 + F
④ 预条件：Jacobi 提取对角线求逆，或 ILU(0) 分解
⑤ 迭代求解：solveCG() / solveBiCGStab()
⑥ 把 u 拷回 CPU
```

**关键优化点是第 ②③ 步的分离：结构只上传一次。** 非线性或瞬态分析里，矩阵的「位置」（哪些位置非零）是不变的，变的只是「数值」。所以行指针、列索引和矩阵描述符只在第一次上传并复用，之后每步只传数值。

> 这里我踩过一个很隐蔽的坑：OpenSees 会先调 `setSize()`（内部把 `m_initialized` 置为 true），再调 `solve()`。我原本用 `if (!m_initialized)` 判断「是否首次调用」，结果 CSR 结构**永远不会上传**，`d_csrRowPtr` 是个垃圾指针，程序崩在 `cublasDdot` 里，cuSPARSE 报 `csrRowOffsets NULL`。修复办法是另立一个独立标志 `m_structureUploaded`。这类「框架调用顺序和你的直觉不一致」的 bug，比算法本身更容易吃掉一个下午。

## 四、Phase A：先让链路跑通

第一版我实现的是最经典的组合：**CG（共轭梯度）+ Jacobi 预条件**。

### CG 在数学上是什么

当 `K` 对称正定（SPD）时 —— 弹性问题就是 —— 解 `K·u = F` 等价于最小化一个二次函数：

```
f(u) = ½·uᵀK·u − Fᵀu
```

CG 的思想是：每一步沿一个与之前所有方向都 **K-正交（共轭）** 的方向前进，这样不会重复走老路。理论上 n 步内到精确解，实际远用不到 n 步。收敛快慢取决于矩阵的条件数 κ：

```
‖eₖ‖ ≤ 2 · ((√κ − 1)/(√κ + 1))ᵏ · ‖e₀‖
```

κ 越小，收敛越快。**预条件的目的就是找一个 M ≈ K，让 M⁻¹K 的条件数比 K 小。** Jacobi 取 `M = diag(K)`，只做一次缩放，对条件数改善有限，但几乎零成本 —— 三次 kernel 调用（提取对角线、求逆、逐元素乘）就完了。

### 一次迭代做了什么

```cpp
r = b - A*x;  z = M⁻¹r;  p = z;
for (k = 0; k < maxIter; k++) {
    Ap = A * p;                  // ← gpuSpMV()，整个求解器的核心
    α  = (r·z) / (p·Ap);         // cublasDdot
    x += α*p;  r -= α*Ap;        // cublasDaxpy
    if (‖r‖ < tol) break;
    z  = M⁻¹ * r;                // 预条件
    β  = (r·z)_new / (r·z)_old;
    p  = z + β*p;
}
```

`A·p` 这一行是核心中的核心。迭代法每一轮本质就是做一次 SpMV，而 SpMV 只遍历非零元 —— 这就是为什么迭代法每步便宜、内存小。

我把它封装成了一个 `gpuSpMV()` 入口，CG 和 BiCGStab 的三处调用点统一走这里。这样底层实现要换（比如换回 legacy API、或者自己写 kernel）只需改一处。

### 先对着解析解验一遍

写完之后第一步不是跑大算例，而是拿一根 10 单元的 2D 悬臂梁，跟解析解 `P·L³/(3EI)` 对比：

| 求解器 | 端部挠度 | 与解析解偏差 |
|---|---|---|
| 解析解 | −11.494252873563218 | — |
| SuperLU（CPU） | −11.494252873552977 | ~9e-12 |
| **cusp CG + Jacobi** | −11.494252873559686 | **~3e-12** |
| **cusp BiCGStab + Jacobi** | −11.494252873937057 | ~3e-11 |

链路通了。接下来才是真正的考验。

## 五、三场景基准：48.7× 到 212×

我设计了三个场景，各有各的用意：

| 场景 | 模型 | DOF | 设计意图 |
|---|---|---|---|
| S1 | 3D 实体悬臂块（18×18×200，stdBrick） | 217,683 | 大规模 SPD，测 CG 的主场 |
| S2 | 3D 多层钢框架（16×16×24，elasticBeamColumn） | 43,350 | 梁单元框架，直接法 fill-in 病态 |
| S3 | 3D 实体块瞬态（10×10×40，Newmark 200 步） | 14,883 | 每步一次求解的累积效应 |

硬件：AMD 9700X + **RTX 5070（12GB，sm_120）** + 32GB 内存，Windows 11 + WSL2，CUDA 12.8。计时用 Tcl 的 `clock milliseconds` 包住 `analyze`。

### 结果

**S1 · 3D 实体悬臂块·静力（217,683 DOF）**

| 配置 | 时间 | 加速比 |
|---|---|---|
| 串行 SuperLU | 203.14 s | 1× |
| **CUDA cusp-CG + Jacobi** | **4.01 s** | **50.7×** |
| 并行 Mumps np=8 | 37.50 s | 5.4× |

**S2 · 3D 多层钢框架·静力（43,350 DOF）**

| 配置 | 时间 | 加速比 |
|---|---|---|
| 串行 SuperLU | 107.53 s | 1× |
| **CUDA cusp-CG + Jacobi** | **0.51 s** | **212×** |
| 并行 Mumps np=8 | 3.72 s | 28.9× |

**S3 · 3D 实体块·瞬态 200 步（14,883 DOF）**

| 配置 | 时间 | 加速比 |
|---|---|---|
| 串行 SuperLU | 464.92 s | 1× |
| **CUDA cusp-CG + Jacobi** | **34.31 s** | **13.6×** |
| 并行 Mumps np=8 | 102.12 s | 4.6× |

GPU 迭代法不仅全面快过串行直接法，也快过了 8 进程并行的 Mumps。

### 三个必须说清楚的限定

第一，**这是异质对比，不是同算法公平对比**。我比的是「GPU + 迭代法」对「CPU + 直接法」，加速比里同时包含硬件差异和算法差异。要单独衡量算法优劣，得拿 GPU 直接法或 CPU 迭代法作对照 —— 这一点我不想含糊过去。

第二，**S2 的 212× 有场景特殊性**。梁单元框架对直接法特别不友好，SuperLU 在这个模型上实测接近 O(n²)，把加速比放大了。这个数字更应该读作「直接法在该问题上的劣势被暴露」，而不是「GPU 普遍快 212 倍」。

第三，**内存优势才是硬优势**。迭代法只存原矩阵的 CSR，没有 fill-in，这是与问题规模无关的结构性优势。上表的加速比会随机器和实现波动，内存这件事不会。

### 正确性：不抽查，全场比

为了不只是「看起来对」，我做了三重验证：

- **对解析解**：悬臂梁端部挠度偏差 ~3e-12（见上一节表格）；
- **对串行 SuperLU 精确解**：三场景所有配置，tip 位移相对偏差 **≤ 1.3e-9**，远优于 Newton 迭代判据 1e-8；
- **全场级比对**：S1 抽 **6317 个位移分量**逐点比较，**最大绝对差 2.06×10⁻¹²，相对偏差 7.8×10⁻¹⁴**。

第三项是我最看重的 —— 验证整个解向量，而不是挑一个点好看。

## 六、Phase B：更强的预条件，和两个坏掉的官方 API

Phase A 之后的问题很清楚：Jacobi 预条件太弱。它只是把矩阵缩放了一下，条件数改善有限。对更难的问题（非对称、病态），需要更强的预条件。于是 Phase B 做 **ILU(0)** 和更通用的 **BiCGStab**。

### ILU(0)：禁止填空的不完全分解

完整 LU 的问题在于填空。ILU(0) 的想法是：**只允许在 K 原本非零的位置上产生 L、U 的非零元，从机制上禁止填空**。这样 L、U 的非零结构和 K 完全一样，内存和 K 同量级，而 `L·U ≈ K`（是近似，不是相等），可以拿来当预条件 `M = L·U`。

实现逐行做三件事：

```cpp
// ① scatter：把第 i 行摊到一个稠密工作数组上
for (p = rowPtr[i]; p < rowPtr[i+1]; p++) {
    w[colInd[p]] = val[p];
    marker[colInd[p]] = i + 1;      // 标记「列 c 出现在第 i 行的模式里」
}

// ② eliminate：消去严格下三角（j < i）
lik = w[c] / diagU[c];              // L(i,c)
for (q in 第 c 行的上三角部分) {
    if (marker[m] == i + 1)         // ★ 只有当 m 本来就在第 i 行里才更新
        w[m] -= lik * val[q];       //   否则就是填空 —— 跳过
}

// ③ gather：写回，val 就地变成 L + U
```

`marker[m] == i+1` 这一行判断，就是 ILU(0) 与完整 LU 的**唯一区别**：它保证只有当列 `m` 本来就出现在第 `i` 行的稀疏模式里时才更新，从而杜绝填空。这个技巧只要理解了，就觉得它简单得有点可爱。

### 三角求解：怎么并行一个「天生串行」的过程

ILU(0) 预条件的应用是解 `M⁻¹b`，其中 `M = L·U`，于是：

```
M⁻¹·b = U⁻¹ · (L⁻¹ · b)
```

前推 `L·y = b` 是**串行的**：`y[i]` 依赖所有 `y[j], j < i`，必须先算完前面所有行。在一个 3D 网格上，这条依赖链会非常长。

但关键在于：**不是所有行都互相依赖**。把依赖关系画成一个有向无环图，对每行算它的「层级」：

```
fwdLevel[i] = max(fwdLevel[j] + 1)，对所有 j < i 且 K(i,j) ≠ 0
```

**同一层里的行互不依赖，可以并行算。** 于是求解器按层推进：

```cpp
for (int l = 0; l < numLevels; l++) {
    for (k = tid; k < nrows; k += nthreads)   // 本层内，线程并行
        y[order[start + k]] = b[i] - Σ L(i,j) * y[j];
    grid.sync();                              // 层间栅栏：本层全算完才进下一层
}
```

这里的关键指标是 **level 数，也就是最长依赖链（临界路径）**。它越小，需要的同步越少、能并行的越多。而 3D 网格在 RCM（Reverse Cuthill-McKee）排序下，这个量是 **O(n²ᐟ³)**。记住这个结论，下一节它就要上场了。

### 坑：sm_120 上两个官方 API 是坏的

这是整个项目里我最想讲的一段。**cuSPARSE 有两个 API，在我这块 RTX 5070（Blackwell，sm_120）上不可用。**

| API | 本该做什么 | sm_120 上的实际表现 |
|---|---|---|
| `cusparseDcsrilu02` | GPU 端 ILU(0) 分解 | 大矩阵（n≥8000）返回 `INVALID_VALUE`，**越界写 CSR 结构数组并清空对角线**，却报成功 |
| `cusparseSpSV` | GPU 端三角求解 | **间歇性 SIGFPE**（浮点异常崩溃），约 7/10 概率 |

怎么定位的，过程比结论更值钱：

1. 崩溃栈指向 `cusparseSpSV ← applyPreconditioner`，但栈本身不能证明是库的问题 —— 也可能是我传错了描述符。
2. 于是写了一个**独立复现器**（一个 7 点 Laplacian，完全脱离 OpenSees）。问题依然稳定复现 → 排除「我的 OpenSees 集成有问题」。
3. 对 `csrilu02` 做**完整性校验**：分解之后，把 CSR 的结构数组（`rowPtr`/`colInd`）从显存拷回主机，和分解前的原始结构 `memcmp` 对比。结果是 **170 万个索引被改写、对角线变成 0** —— 实锤越界写，而且状态码还报成功。这个「拷贝回 CPU + memcmp」的手法，比盯着崩溃栈猜有用得多。
4. 修复：**弃用这两个 API，全部自实现** —— ILU(0) 分解改到 CPU 端用普通 C++ 循环做（就是上面那段 `marker` 逻辑），三角求解改成 level-scheduled 的 cooperative kernel。

顺带一提，CUDA 12 已经删除了全部 legacy cuSPARSE API（`cusparseDcsrmv`、`csrsv2` 这些），所以 SpMV 也必须迁移到 generic API `cusparseSpMV`。这两个版本迁移加上平台的库 bug，构成了这个项目大部分的非算法工作量。

## 七、最反直觉的结果：ILU(0) 反而更慢

Phase B 做完，ILU(0) 的数值全部正确（偏差 ≤ 1.3e-9），稳定性问题也解决了。但性能上出现了完全反直觉的结果：

| 场景 | cusp-cg（Jacobi） | cusp-ilu0-cg | 倍数 |
|---|---|---|---|
| S1 实体（217,683 DOF） | 4.01 s | 51.79 s | **慢 12.9×** |
| S2 框架（43,350 DOF） | 0.51 s | 3.06 s | 慢 6.0× |
| S3 瞬态（14,883 DOF） | 34.31 s | 64.37 s | 慢 1.9× |

ILU(0) 明明把 CG 的迭代次数压到了 **2.3 倍**（8×8×40 规模：94 次 vs 219 次），为什么总时间反而更慢？

原因是：**每次预条件（三角求解）的开销是 Jacobi 的约 25 倍**。迭代红利被每步变贵完全抵消，还倒亏。

接下来是我在答辩里最想展示的部分 —— **我没有停在「ILU0 就是慢」这个结论上，而是把瓶颈测了出来**。

### 假设 → 实验 → 定位

**第一次假设：kernel launch 开销。** level-scheduled 求解有 786 个 level（8×8×40），按最朴素的实现就是 786 次 kernel launch。786 次启动延迟，听起来很像主因。

**实验 1**：把 level 循环整个搬进一个 persistent kernel，消除那 786 次 launch。

**结果**：2.237 s → 2.025 s，只快了约 10%。**假设否定。**

**第二次假设：单 block 带宽/占用不足。** 那就换成全网格常驻的 cooperative persistent kernel，用逐 level 的 `grid.sync()` 做栅栏。

**实验 2：** S1 上 51.79 s → 51.27 s，**完全没有改善**；小规模反而更慢。**假设再次否定。**

**定位：真正的瓶颈是依赖临界路径本身。**

前推/后推按依赖 DAG 分层，层数实测 **786**（8×8×40，n=9963）、**~6972**（S1，n=217,683），随规模呈 **O(n²ᐟ³）** 增长。层数多 + 每层活跃行数少（占用低）+ 每层都要全网格同步，这三个因素叠加，就是每次 apply 是 Jacobi 25 倍的根源。

这是一个**结构性**问题，不是实现技巧能绕过去的 —— 3D 网格的三角求解并行度本来就受临界路径限制。

**所以我最终的结论是：在 SPD 问题上，ILU(0) 没有价值；它真正的价值应该在非对称、病态的问题上（接触、不可压缩、大变形切线刚度非对称）。** 而那类场景我还没有建 benchmark —— 这是这个项目最大的空白，我在答辩时也把它明确列为未完成项。

> 两次实验都否定了「launch 开销」这个最常见的猜测。**瓶颈是测出来的，不是猜出来的。** 这句话是我在整段工作里收获最大的东西。

## 八、结论与下一步

**做成了什么：**

1. **正确性**：GPU 解在三个场景上与串行 SuperLU 相对偏差 ≤ 1.3e-9，全场级验证最大绝对差 2.06e-12。
2. **性能**：GPU 迭代法全面领先 CPU 直接法（13.6× – 212×），且内存 O(nnz)、无 fill-in。
3. **方法论**：用「独立复现器 + memcmp 完整性校验」定位厂商库 bug；用「假设 → 实验 → 定位」量化性能瓶颈 —— 这套流程比任何一个加速比数字都更能复用。
4. **边界认知**：ILU(0) 在 SPD 问题上不划算，Jacobi + CG 已经是最优解；ILU(0)/BiCGStab 的价值要另找场景。

**下一步（按性价比排序）：**

| | 方向 | 预期 |
|---|---|---|
| A | **置换重排**：把临界路径从 RCM 的 O(n²ᐟ³) 压向图直径 O(n¹ᐟ³) | 不动预条件，收敛行为不变，叙事最漂亮。注意：我试过朴素单源 BFS，只降了 786→687（~12%），因为 stdBrick 单元耦合对角节点、同一 BFS 壳层内仍留长链，需要更讲究的「对角双源」波前序 |
| B | **块 Jacobi ILU(0)**：沿长轴分块，各块独立分解 + 并行求解 | 牺牲少量收敛换彻底并行，GPU 上最常用的 ILU 提速手段 |
| C | **稀疏近似逆 SPAI**：把预条件做成稀疏矩阵，apply 退化成一次 SpMV | 彻底绕开三角求解的串行依赖 |
| D | **非 SPD 场景验证** | 给 ILU(0)+BiCGStab 找到真正该用的地方 —— 当前最大的空白 |
| E | SPD 场景改用 **IC(0)**（`M = L·Lᵀ`，对称） | 省掉一半三角求解 |

**还有几条工程上的血泪经验，顺便记在这里：**

- `.cpp` 里写了 `<<<>>>` kernel 语法，CMake 必须给这个文件设 `LANGUAGE CUDA`；而且 `set_source_files_properties` 里的 `TARGET_DIRECTORY` 必须是**独立参数**，写进 `PROPERTIES` 列表会被静默忽略（我在这上面浪费了很久）。
- 根 CMake 漏了 `enable_language(CUDA)`，属性不生效，g++ 直接去编译 kernel 语法，报 `blockIdx was not declared`。
- CUDA 构建必须**禁用** `-static-libstdc++`。否则可执行文件静态链接了 libstdc++、拥有自己一份 `std::cerr`，和 CUDA 的链接布局叠加后该对象的 vtable 保持 NULL —— 程序连 `puts "hello"` 都会段错误。这个 bug 我是靠 gdb 一路追到 `std::ostream::sentry` 才找到的。
- CUDA 12.0 上，如果 `cusparseCreate` 是进程里第一个 CUDA 调用，会直接失败（`CUDA context cannot be initialized`）。构造函数里先随便调一次 `cudaGetDeviceCount()` 就正常了。
- WSL 下如果 `/lib/x86_64-linux-gnu/` 里有一个手动装的 Linux 原生驱动库，它会抢占 `libcuda.so.1`，导致枚举不到 GPU（`no CUDA-capable device is detected`）。而 WSL 里 GPU 只能通过 `/usr/lib/wsl/lib/libcuda.so.1` 这个转发 Windows 驱动的 shim 访问。

## 九、复现

代码仓库：[OpenSees-GPU-Solver](https://github.com/Tilyes/OpenSees-GPU-Solver)（Public，含完整源码与 `plan/` 过程文档）

```bash
# 构建（WSL，CUDA 12.8+）
cmake -S . -B build-cuda -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_ARCHITECTURES="89;120"
cmake --build build-cuda --target OpenSees -j8

BIN=build-cuda/OpenSees

# Phase A：CG + Jacobi
$BIN bench/models/s1_brick_static_ilu0.tcl cusp-cg 18 18 200

# Phase B：ILU0 + CG / ILU0 + BiCGStab
$BIN bench/models/s1_brick_static_ilu0.tcl cusp-ilu0-cg       18 18 200
$BIN bench/models/s1_brick_static_ilu0.tcl cusp-ilu0-bicgstab 18 18 200

# 基线：串行 SuperLU / 并行 Mumps
OpenSees bench/models/s1_brick_static_ilu0.tcl superlu 18 18 200
mpiexec -np 8 build-hypersp/OpenSeesSP bench/models/s1_brick_static_ilu0.tcl mumps 18 18 200
```

Tcl 里的求解器用法：

```tcl
system cusp -pre {none|jacobi|ilu0} -solver {cg|bicgstab} -rtol 1e-8 -maxIter 20000
```

仓库里的 `plan/` 目录是完整过程记录，包括实施日志、基准日志、`spsv_fpe_repro.cu`（sm_120 坏 API 的独立复现器），以及一份从零讲 CG / ILU(0) / level scheduling 原理与代码走读的学习指南。

## 十、最后：关于「站在别人的肩膀上」

这个项目给我最深的印象，不是某个加速比数字，而是**边界感**。

OpenSees 是一个有二十多年积累、被写成教科书的框架。我做的事情，本质上是在它已经很成熟的躯干上接了一个 GPU 求解器。真正难的地方不在写 CG 的迭代循环 —— 那是教科书上的东西 —— 而在于：搞清楚框架内部的调用顺序和隐含约定（比如「行首必须是对角元」「`setSize` 在 `solve` 之前」），判断一个失败到底是我的错还是厂商库的错，以及在拿到一个反直觉的性能结果时，不去编一个听起来合理的解释，而是把它测出来。
